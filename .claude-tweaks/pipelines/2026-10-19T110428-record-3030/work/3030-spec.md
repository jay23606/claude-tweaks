# 3030: check-sibling-sessions: `--record N` reads only local worktree locks, never the claims registry

Surface: infra

**Related:** #3131, #3032

## Current State

`hooks.js check-sibling-sessions --record N` only sees siblings whose worktrees are on this machine and whose lock or branch name carries the record. It never reads the claims registry.

- The handler (`plugin/bin/hooks.js:1262`) calls only `siblingSessions.findConflictingSession(recordRef, { cwd })` (`hooks.js:1277`).
- That function (`plugin/bin/lib/hooks/sibling-sessions.js:129`) parses `git worktree list --porcelain` and keeps in-use locked entries whose branch/path tokens match the record. The module exports only `findConflictingSession`, `matchesRecordRef`, and `tokenize` (`sibling-sessions.js:161`).

A sibling still holds a live `claims-registry` blob for the record when it is on another machine, in a cloud session, has an unlabeled worktree, or claimed but has not yet created its worktree. In each of those cases the check prints `no sibling-session conflict found`. The contest surfaces only at `/claude-tweaks:flow` Step 2.8's atomic claim (`bin/claim-targets.js`, exit 3), inside the group's first Task call. By then dispatch has already minted a run dir, created a worktree, and launched the Task. #3131 is a live instance of exactly that late contest.

`plugin/skills/dispatch/sibling-session-check.md:28` also still says the check is "additive to the existing branches/claims/labels check that follows in Step 4". Step 4 has no claims check any more, because claiming lives in flow's Step 2.8.

The read path needed already exists:

- `readClaimBlob(deps, repoSlug, issueNumber)` (`plugin/bin/lib/issues/claim-store.js:213`) tries git-CAS against `origin` first and falls back to the contents API (`defaultGhApi`, `claim-store.js:148`).
- `classifyClaimBlob(content, now)` (`plugin/bin/lib/issues/claims.js:112`) classifies the blob.
- `defaultRunner` (`claims-git-cas.js:76`) and `repoSlugOf` (`hooks/git-exec.js:179`) provide the deps.

## Deliverables

1. Add `findLiveClaim(recordRef, opts)` to `plugin/bin/lib/hooks/sibling-sessions.js` and export it.
   - Reads the record's claim blob through the existing `readClaimBlob`, with `classifyClaimBlob` deciding liveness.
   - Returns `{ runId, sessionId, host, claimedAt }` only for a `live` claim held by a session other than `CLAUDE_CODE_SESSION_ID`.
   - Fails open to `null` on a non-numeric (slug) ref (no read at all), a read failure or throw, an absent blob, a tombstone, a stale claim, unparseable content, or this session's own claim.
   - Takes an injectable `readClaim`, `sessionId`, and `now` for tests.
2. The `check-sibling-sessions` handler in `plugin/bin/hooks.js` calls `findLiveClaim` only when the worktree check found nothing. On a hit it prints `claude-tweaks: sibling session may already hold record {ref} — live claim by run … (session …, host …, claimed …); verify before claiming`. This is the same prefix the worktree branch uses, so `sibling-session-check.md`'s branching is unchanged.
3. `plugin/skills/dispatch/sibling-session-check.md` describes both sources for the may-already-hold line. It replaces the stale "additive to the existing branches/claims/labels check that follows in Step 4" sentence with the accurate one: the check is advisory, and flow Step 2.8's atomic claim remains the correctness boundary.
4. `tests/hooks-sibling-sessions.test.js` gains two tests. One shows a live foreign claim being reported with its identity. The other shows the fail-open cases all returning `null`, including a slug ref never triggering a read.

## Acceptance Criteria

- With a live claim blob for #77 held by session `sibling`, `findLiveClaim('77', { sessionId: 'me' })` returns that claim's `{ runId, sessionId, host, claimedAt }`, and `findLiveClaim('#77', …)` does the same.
- `findLiveClaim` returns `null` in each of these cases:
  - for the caller's own session's claim
  - for a released tombstone
  - for a stale claim past its TTL
  - for an absent blob
  - for unparseable content
  - when the reader throws
  - for a slug ref like `flow-spec-12`, where the reader is never invoked
- `check-sibling-sessions --record N` prints the may-already-hold line naming the live claim when only a remote or foreign claim exists. It keeps printing the worktree-lock line, unchanged, when a local locked worktree matches.
- `sibling-session-check.md` no longer references a Step 4 claims check and names flow Step 2.8 as the correctness boundary.
- `node --test tests/hooks-sibling-sessions.test.js tests/hooks-help-guard.test.js` passes.

## Release Note

Dispatch now notices when another session, including one on a different machine, already holds a record's claim, before it sets up a worktree for it.

## Technical Approach

The fix reuses the claim system's own read and classify functions rather than adding a separate claim reader, so the sibling check and the claim write can never disagree about what "live" means. Placement after the worktree-lock check keeps the cheap local check first. The extra read happens only when no local sibling was found: one single-ref `git fetch`, or one contents-API call per group member. The check stays advisory and fails open. It exists to stop dispatch from wasting a run dir and worktree, not to replace flow Step 2.8's atomic claim, which stays the correctness boundary. A false "no conflict" therefore costs only the late contest that happens today. The original request below carries the reporter's full diff. The reporter also checked live through the patched module that it reported a sibling's claim which the worktree check missed.

### Key Files

- `plugin/bin/lib/hooks/sibling-sessions.js` — new `findLiveClaim` (+ default claim reader) and export
- `plugin/bin/hooks.js` — `check-sibling-sessions` handler falls through to `findLiveClaim` when no worktree conflict
- `plugin/skills/dispatch/sibling-session-check.md` — both conflict sources; stale Step 4 sentence corrected
- `tests/hooks-sibling-sessions.test.js` — live-foreign-claim and fail-open tests

## Gotchas

- `readClaimBlob` is synchronous today (`claim-store.js:213`). Keep `findLiveClaim` synchronous so the handler's control flow stays a plain if/else. If `readClaimBlob` ever turns async, the handler must await it.
- The default reader requires `claim-store`, `claims-git-cas`, and `git-exec` lazily inside the closure, so `findConflictingSession`-only callers and the test file don't pay the load cost or need network deps.
- Exclude the caller's own session by `sessionId` only when `CLAUDE_CODE_SESSION_ID` is set. With no session id, every live claim reads as foreign. That is acceptable for an advisory check, but note it in the module comment.
- `tests/hooks-help-guard.test.js` pins the CLI's usage table (`hooks.js:93`). No usage text changes here, so the suite should stay green. Re-run it anyway.

check-sibling-sessions: `--record N` reads only local worktree locks, never the claims registry

**Summary:** check-sibling-sessions --record N only reads local worktree locks, never the claims-registry, so a sibling on another machine or with an unlabeled worktree is missed until flow Step 2.8

**Kind:** Defect

**Affected component:** hooks.js check-sibling-sessions (bin/lib/hooks/sibling-sessions.js) + dispatch/sibling-session-check.md

**Repro steps:**
1. Session A claims record #N (live blob on `claims-registry`) from another machine, a cloud session, or with a worktree whose name/lock does not carry the record — or has claimed but not yet created its worktree.
2. Session B runs `/claude-tweaks:dispatch #N`; Step 4 runs `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" check-sibling-sessions --record N`.

**Expected vs. actual:**

Actual: `no sibling-session conflict found for record N`. The live claim surfaces only at `/claude-tweaks:flow` Step 2.8's atomic claim (`bin/claim-targets.js`, exit 3) inside the group's first Task call — after dispatch has already minted a run dir, created a worktree and launched the Task.

**Root cause:** `bin/hooks.js:1262-1288` calls only `siblingSessions.findConflictingSession`, which (`bin/lib/hooks/sibling-sessions.js:129-159`) parses `git worktree list --porcelain`, keeps `lockVerdict === 'in-use'` entries whose branch/path tokens contain the record ref, and excludes this session's own worktrees; the module header (`:1-22`) is explicit that it does not look at claims. Also `dispatch/sibling-session-check.md` still says the check is "additive to the existing branches/claims/labels check that follows in Step 4", but Step 4 no longer has a claims check (SKILL.md: "Claiming ... all live in `/claude-tweaks:flow`'s Step 2.8"). Fix: add `findLiveClaim()` using the same `claim-store.readClaimBlob` the claim write path uses (git-CAS against `origin` first, so GHE works; contents API fallback) and the same `classifyClaimBlob`, excluding this session's own claim. `check-sibling-sessions` reports a live foreign claim with the same `sibling session may already hold record...` prefix, so `sibling-session-check.md`'s branching is unchanged. Fails open (non-numeric refs, read failures, unparseable blobs -> null). The patch also corrects the stale Step 4 sentence.
