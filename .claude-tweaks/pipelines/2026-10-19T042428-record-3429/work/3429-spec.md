# 3429: Windows regression: 2 test file(s) newly failing after a39cd61fa

Surface: infra

## Current State

`.github/workflows/windows-regression.yml` flagged two test files that newly fail on `windows-latest` after a39cd61fa (#3348, which shipped #3306's skill-size rail work together with #3307 and #3309). Both files were added by that merge, so they have no earlier Windows baseline. Both failures are test-side defects that only show up on a Windows checkout. The production CLIs are not at fault.

1. **`tests/load-delta-cli.test.js:373`**, "review summary template carries the Skill Load Delta section and a compact-form line". It reads `plugin/skills/review/review-summary-template.md` with a raw `fs.readFileSync(..., 'utf8')` (line 374) and asserts `/### Skill Load Delta\n/` (line 376). The heading exists at `review-summary-template.md:156`. On a Windows checkout, Git's default `core.autocrlf=true` writes the file with `\r\n`, the run's excerpt shows `'## Full template\r\n'`, and `\n` never directly follows `Delta`. This repo's `.gitattributes` pins only `tools/upstream-drift/fixtures/**`. The same file reads two more governed markdown files raw: `code-mode-steps.md` at line 343 (that test's `replace(/\n+$/, '')` and `split('\n').length <= 4` count is also line-ending sensitive) and `step3-skill-load-delta.md` at line 354 (`includes` checks on single lines, so it is CRLF-safe today). `tests/helpers/read-skill.js`'s `readText()` (#2763) is the house EOL-normalizing read for exactly this case. This file does not import it.
2. **`tests/skill-load-report-cli.test.js:105`**, "an unreadable main transcript is counted, and with none read the result is no-data". It simulates an unreadable transcript with `fs.chmodSync(file, 0o000)` (line 109) and expects `unreadable: 1, rows: []`. On win32, Node's `chmod` only toggles the read-only attribute and never denies reads. So `readSkillLoads` (`plugin/bin/lib/skill-audit/transcript-load.js:114`, called from `plugin/bin/skill-load-report.js`'s `read` closure) reads the file fine, and the run's excerpt shows `+ rows: [` (data was read). The sibling test at line 118, "an unreadable subagents/ directory is counted and the run continues", uses the same `chmodSync(dir, 0o000)` simulation (line 123) and expects `unreadable: 1`. It cannot hold on win32 either, but the run's excerpt shows only the first failure per file. Both tests already carry `skipUnderRoot('mode bits are ignored under root')` from `tests/helpers/root.js`. That guard is keyed only to `process.getuid() === 0`, which is never true on win32 (`getuid` is undefined there).

## Technical Approach

- **CRLF read (Deliverable 1).** Use the established `readText()` helper rather than loosening each regex to `\r?\n`. The helper's own header names prose-conformance suites that read governed markdown as its mandate, and #3113 routed 17 suites through it for the same class of failure. Changing the regexes would fix only line 376 and leave the line-343 line count exposed.
- **Permission simulation (Deliverable 2).** Rejected alternative: add an injectable reader to `skill-load-report.js`'s `run(argv, deps)` seam, so a throwing reader drives the `unreadable++` branch on every platform. That would add a production seam purely for a test. The branch is platform-neutral code that the POSIX run already covers. The project skill `windows-checkout-test-parity` treats behavior that only one platform can produce as a stated-reason `skip`, the same pattern as `tests/bin-lib/visual-decide/cli.test.js:127` and `tests/bin-lib/verify/cli.test.js:2286`. Combine the win32 condition with the existing root predicate in each test's options object, and keep the `skipUnderRoot(` reference that the conformance scan requires. Do not change `skipUnderRoot`'s semantics in `tests/helpers/root.js`. It is a shared helper used by about 25 chmod-using test files, and widening it is a separate decision (see Gotchas).

### Key Files

- `tests/load-delta-cli.test.js`: import `readText`, and replace the three raw `REVIEW` reads (lines 343, 354, 374)
- `tests/skill-load-report-cli.test.js`: add the win32 skip condition to the two chmod-based tests (lines 105, 118)
- `tests/helpers/read-skill.js`: read-only reference (the `readText()` helper being adopted)
- `tests/helpers/root.js`: read-only reference (`skipUnderRoot`, which stays unchanged)
- `tests/permission-sim-root-skip-conformance.test.js`: read-only reference (the scan the edited file must keep satisfying)

## Gotchas

- `tests/permission-sim-root-skip-conformance.test.js` passes a file only if it both imports `tests/helpers/root.js` and contains the text `skipUnderRoot(`. Replacing the call wholesale with a hand-rolled `{ skip: ... }` breaks that scan. Keep the call and combine its `.skip` with the win32 condition.
- Never stub `process.platform` to test the win32 skip. It is process-global and leaks into other tests in the same worker (`windows-checkout-test-parity`'s Anti-Patterns).
- Other chmod-based permission tests (about 25 files call `chmodSync`) probably have the same win32 blind spot. They sit inside the existing Windows baseline failure set that #2767 tracks, so they are out of scope here. Widening the shared helper to also skip on win32 belongs to that record or a new one, not this fix.
- The Windows-regression excerpt shows only the first failing test per file. Confirm the line-118 and line-343 tests on the next `windows-latest` run rather than assuming they are fixed.
