# 3731: wrap-up Section D never proves the recorded pid or port belongs to the server it recorded

Surface: infra

Origin: ledger resolve gate (wrap-up of #3664, ledger rows 3-4)
**Related:** #3664, #3646, #3792, #3942

## Current State

The ephemeral dev server a pipeline starts (`_shared/dev-url-detection.md`'s Ephemeral server start, items 3-4) is recorded as one line, `{pid} {port} {worktree-root} detached:{yes|no}`, in `ephemeral-server.txt`. POSIX launches under `setsid` and records `detached:yes`; Windows has no detach primitive and records `detached:no` (`dev-url-detection.md:130-131`). The recorded pid is the shell leader; the listening socket can belong to its child.

Every stop identifies the server only by that pid and port. `wrap-up/cleanup-procedures-execution.md` Section D (#3664) validates the record's shape and keeps it when the port is still held after the kill, but proves neither identity:

- **Kill side (step 2):** any positive-integer pid is signalled (`kill {pid}`, plus `kill -- -{pid}` under `detached:yes`; `taskkill /PID {pid} /T /F` on win32). A pid reused by an unrelated process after the server died gets killed, along with its tree on win32.
- **Port side (step 4):** a port still held after an "already stopped" pid is reported as the server's survivor, though the holder may be an unrelated process.

A "pid listens on port" probe does not settle it, because the listener is usually the leader's child, and after the leader dies a non-detached child is reparented, so a parent-chain walk breaks.

The same stop logic is restated as agent-read prose in other places: `review/step3-routing.md`'s fix-wave server coordination (around line 124), `_shared/dev-url-detection.md`'s standalone stop, `flow/multispec-review-console.md`'s shared teardown (line 176), and `flow/multispec-parallel-waves.md`'s per-member stop (line 54). Each guard is pinned by text, not by behavior.

## Technical Approach

The two candidate rules in the original question were a pid-listens-on-port probe (it fails for the shell-leader/child shape, as the record notes) and some stronger identity. Start time is the standard way to tell a reused pid from the original. POSIX: `ps -o lstart= -p {pid}` or `ps -o etimes=`; win32: `Win32_Process.CreationDate` via PowerShell `Get-CimInstance`. A reused pid cannot share its predecessor's start time. Capturing the listener's own identity at start, instead of deriving it from the leader at stop, sidesteps the reparenting problem entirely.

Listener lookup at record time: POSIX `lsof -nP -iTCP:{port} -sTCP:LISTEN -t`, with `ss -ltnp` as a fallback where `lsof` is absent; win32 `Get-NetTCPConnection -LocalPort {port} -State Listen` → `OwningProcess`.

Fail direction: an identity the helper cannot read (no `ps`, a CIM failure) is unprovable, so it signals nothing and reports a cleanup failure, keeping the record. A leaked dev server is recoverable; a killed unrelated process is not.
