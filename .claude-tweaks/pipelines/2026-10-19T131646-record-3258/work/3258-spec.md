# 3258: PR-check gate: demote checks already red on the integration tip to a caveat

Verified-as-of: d81250829ae2c3db172448be1f3588da29b78222

Origin: ledger resolve gate

Defer-reason: genuinely-larger

## Current State

Under `integration-model: pr-first`, `/claude-tweaks:test`'s pipeline gate and `/claude-tweaks:review` Step 1.5 run `bin/pr-checks.js` (#3013) and stop on `state: red`. A check that is already failing on `origin/{integration-branch}`'s tip is inherited by every branch cut from it, so every pr-first run in that window stops at `/test` for a failure its diff did not cause.

Local verification already separates inherited from attributable failures (`verify.js --baseline` adjudication); this gate does not. `plugin/skills/_shared/pr-check-gate.md` names the inherited case in prose only (catch the branch up instead of debugging the diff), and `plugin/bin/lib/pr-checks/classify.js` has no base comparison.

## Deliverables

- `bin/pr-checks.js`: when the PR read is `red`, also read the integration branch tip's check runs (`gh api repos/{owner}/{repo}/commits/{sha}/check-runs` or equivalent) and report each failing check as `inherited` when the same check name is failing at the base tip, `attributable` otherwise.

- `bin/lib/pr-checks/classify.js`: a pure helper that partitions the failing list against the base's failing names; a new `inherited-red` state (or an `inherited` flag per failing entry) when every failing check is inherited.

- `_shared/pr-check-gate.md`: route all-inherited red as a caveat (AUTO line naming the base tip and checks), not a gate failure; mixed red still fails on the attributable checks only.

- Tests in `tests/bin-lib/pr-checks/` for all-inherited, mixed, and base-read-failed (fails closed to plain red).

## Acceptance Criteria

- [ ] A PR whose only failing check is also failing at the integration tip passes `/test`'s gate with a logged caveat naming the base sha and check.

- [ ] A PR with one inherited and one new failing check still stops, naming only the new check as the cause.

- [ ] An unreadable base tip leaves the read as plain `red` (never green).

## Release Note

pr-first runs no longer stop at /test when the only red check on their PR is one already failing on the integration branch; the gate reports it as inherited and continues.

## Build notes (Common Step 4.5 — Beneficial deviations)

- The base compared is the PR's own `baseRefName` (the branch CI merges against), falling back to the shared integration-branch resolver only when the PR view carries none — a resolver-only base can name a different branch than the PR targets and mislabel a check inherited (final whole-branch review finding).
- "Integration tip's check runs (or equivalent)" is read as check runs + commit statuses + workflow runs, so a base failure surfacing only as a workflow name (the `e91df452c` shape: job `file`, workflow `windows-regression`) still matches.
- A failed head-runs read never concludes `inherited-red` — it reports `read-failed`, the same #3405 rule that already applied to green/pending.
- Output adds `baseBranch`, `baseSha`, `baseReason` and per-entry `inherited` alongside the `inherited-red` state (the Deliverable offered state or flag; both shipped).
