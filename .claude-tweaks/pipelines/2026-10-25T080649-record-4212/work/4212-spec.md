# 4212: Make the hook tokenizer escape-aware so a backslash-escaped quote does not end a quoted span

Origin: ledger resolve gate (run 2026-10-24T200414-record-4015, refs #4015)

Defer-reason: genuinely-larger

## Current State

`plugin/bin/lib/hooks/git-command.js`'s `tokenize` splits a command with the regex `/"([^"]*)"|'([^']*)'|(\S+)/g`, so a backslash-escaped quote inside a double-quoted span ends the span early. `echo "a\" b>c "` is one quoted word in bash, but the tokenizer reads `a\` and then the bare text `b>c` and resolves the write target `c`, a false-positive deny.

The limit predates #4015, but the glued-redirect scan lets more strings reach it. Every parser that reads tokens (`gitTargets`, `fileWriteTargets`, `mkdirTargets`, `teardownTargets`) shares `tokenize`, so the fix has to keep their token values stable for every existing shape; that is why it was not folded into #4015.

## Deliverables

- [ ] Teach `tokenize` that a backslash escapes the next character inside a double-quoted span and outside quotes, and decide what token value an escaped quote yields (the unescaped character, matching bash).
- [ ] Check every parser that reads `tokenize` output against the new values, and add the escaped-quote shapes to `tests/hooks-git-command.test.js` and `tests/hooks-gate-coverage.test.js`.

## Acceptance Criteria

`fileWriteTargets('echo "a\" b>c "', '/r')` returns no target, and `fileWriteTargets('echo foo>x', '/r')` still returns `/r/x`; both are pinned in `tests/hooks-gate-coverage.test.js` and the escaped-quote case goes red when the change is reverted.

The full `npm test` run passes with no change to the expected targets of any existing `gitTargets`, `mkdirTargets` or `teardownTargets` case.

## Release Note

The hook command parser now honours a backslash-escaped quote, so a quoted string containing `\"` and a `>` no longer reads as a redirect.

- `tests/hooks-git-command.test.js` — pin escaped-quote token values
- `tests/hooks-gate-coverage.test.js` — pin the false-positive case
