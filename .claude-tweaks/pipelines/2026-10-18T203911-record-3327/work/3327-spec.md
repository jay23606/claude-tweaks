# 3327: wrap-up: the ledger bulk-resolve fast path accepts deferred rows with no staged proposal

Origin: reflect full (batch) from #3072,#3003

Defer-reason: tangential

**Related:** #3297

## Current State

`_shared/ledger-format.md` defines `deferred` as "staged as a work record proposal … resolved at the run's Queue writes surface", and requires the resolution text to name the origin, affected files, and revisit trigger. `wrap-up/nothing-left-behind.md`'s bulk-resolve fast path checks only `acknowledged` rows for a staged proposal, and `bin/lib/wrap-up/pack.js` `parseLedger` counts every `deferred` row as terminal.

Superpowers' subagent-driven-development parks minor findings in the ledger as `deferred` with only a triage reason. In run 2026-10-16T172900-spec-3072-3003, seven such rows passed #3072's wrap-up gate. They were caught only at the final spec's gate (ledger item 21); otherwise they would have been dropped silently.

## Deliverables

Have `parseLedger` and the fast path flag any `deferred` row whose resolution names neither a staged-proposal path nor a record reference.

Route a flagged row to the resolve gate's Phase 2, or stage a proposal for it, instead of bulk-resolving it.

## Acceptance Criteria

A pack test whose ledger holds a `deferred` row with no `staged/…` path and no `#N` reference reports it (e.g. `deferredUnstaged: 1`), and the fast path no longer treats that ledger as fully resolved.

A `deferred` row that names `staged/…` or `#N` stays terminal.

## Release Note

Wrap-up no longer lets a "deferred" ledger item close without a staged follow-up.
