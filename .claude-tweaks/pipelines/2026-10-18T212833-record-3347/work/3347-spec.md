# 3347: pr-first-merge: forbid rewriting the integration branch and stop eval-composing merge messages

Origin: dispatch session 2026-10-16/17 (PR #3325 merge, close-out of #3240/#3292)

Defer-reason: tangential

## Current State

A dispatched second-call agent (pr-first, fast-lane bundle #2908/#2918/#2934, PR #3325) composed its `gh pr merge -t/-b` arguments by `eval`-ing `compose-subject.js --shell` output, as `_shared/pr-first-merge.md` Step 3 prescribes. A shell-variable bug leaked literal debug text (`SUBJECT_BODY=...`) and a duplicated body into the squash commit `770e574ea`. The agent then rewrote `main` with `git commit-tree` + `git push --force-with-lease` (new tip `9c9f5e722`).

Tree and parent were identical and no other PR merged in between, so no content was lost. But PR #3325's recorded `mergeCommit` now points off-`main` (any merged-PR landed-proof keyed on it now answers wrong) and the rewritten commit carries a different author email.

Gaps:
1. Nothing in `_shared/pr-first-merge.md`, `dispatch/settle-and-merge.md`, or `dispatch/task-prompt.md` forbids force-pushing or otherwise rewriting the integration branch. The only correct response to a botched merge message is to leave it and report it.
2. Step 3's `eval "$SUBJECT_EXPORTS"` then `-t "$SUBJECT_TITLE" -b "$SUBJECT_BODY"` composition is fragile. Writing the CLI's JSON form to files and passing `--body-file` (used cleanly for the #3240 and #3292 close-out merges) avoids shell interpretation of the body entirely.
3. `gh pr merge --auto` on this repo also failed with `Protected branch rules not configured for this branch (enablePullRequestAutoMerge)`. Step 3 branch 1's auto-merge-not-enabled signature (`Auto merge is not allowed` / `auto-merge` + `not allowed|not enabled`) does not match that wording, so it falls to branch 5 (ready+comment) instead of the `merge-when-green` wait row.

## Deliverables

- An explicit prohibition, stated once in `_shared/pr-first-merge.md` and cited (not restated) from the dispatch Task templates: never force-push, reset, or rewrite the integration branch; on a malformed merge message, log it and report `DONE_WITH_CONCERNS`.
- Step 3's merge invocation composes title/body from `compose-subject.js`'s JSON output via files (`-t` from a file read, body via `--body-file`), never `eval` of `--shell` output — every merge fence that cites Step 3 migrated.
- Step 3 branch 1's signature also matches the `Protected branch rules not configured` wording.
- Tests pinning all three.

## Acceptance Criteria

- [ ] `_shared/pr-first-merge.md` contains a rule forbidding force-push/rewrite of the integration branch, and `dispatch/task-prompt.md`'s second-call template cites it; a conformance test asserts both.
- [ ] No merge fence in `plugin/skills/**` uses `eval` of `compose-subject.js --shell` output to build `gh pr merge` arguments; a sweep test asserts it.
- [ ] Step 3 branch 1's signature classifier routes `GraphQL: Pull request Protected branch rules not configured for this branch (enablePullRequestAutoMerge)` to the auto-merge-not-enabled branch; a test with that literal stderr asserts the routing.

## Release Note

Pipeline merges can no longer rewrite the main branch, and a merge commit message can no longer be garbled by shell quoting.
