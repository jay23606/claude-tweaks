# 2887: wrap-up-pack.js's ledger probe can match an unrelated run's ledger file

Surface: infra

## Current State

`ledgerProbe` in `plugin/bin/lib/wrap-up/pack.js:366-418` reads `{run-dir}/ledger.md` first. When that file is absent, it falls back to every `*-ledger.md` under `{worktree}/docs/plans/` (`:378-379`) and picks among them with two heuristics:

- **Exactly one candidate**: the probe treats it as "unambiguously this run's" (`:380-388`), without checking.
- **Two or more candidates, none naming one of this run's records at a `-{n}-`/`-{n}.` boundary** (`namesRecord`, `:362-364`): the probe counts **every** candidate (`:396`), deliberately failing toward over-counting (#2563).

Both heuristics assume the only ledgers in `docs/plans/` are this run's own. That is false in this repo. Finished runs' ledgers stay committed on `main` (for example `docs/plans/2026-10-03-record-2853-ledger.md` and `docs/plans/2026-10-04-record-2772-ledger.md` are tracked today), so every new worktree branched from `main` inherits them. A run that never created its own docs/plans ledger therefore gets either a stranger's ledger counted as its own (one candidate) or all the strangers' ledgers summed (several candidates). This is what happened on #2852's wrap-up: `pack.ledger` reported an unrelated, still-active run's ledger.

## Deliverables

1. Attribute ledgers to the run by ownership, not by filename heuristics. Treat a `docs/plans/*-ledger.md` as this run's only when this run's branch added or modified it relative to its merge base. Keep `namesRecord` only as a secondary tie-break among owned candidates.
2. When no candidate is owned by this run, report zero items. Also expose the unattributed candidates in a distinct field (for example `unattributedFiles`) so a human can still see them. Never sum them into `open` or `total`.
3. Update `pack.test.js` with cases for: one inherited (unowned) ledger, several inherited ledgers with none owned, one owned ledger alongside inherited ones, and the `{run-dir}/ledger.md` precedence (unchanged).

## Acceptance Criteria

- A worktree whose `docs/plans/` holds only ledgers inherited from the merge base gets `pack.ledger` with `open: 0`, `total: 0`, and those files listed under the unattributed field, not under `files`.
- A worktree with one ledger added on its branch plus inherited ledgers counts only the added ledger's items.
- `{run-dir}/ledger.md`, when present, still takes precedence with unchanged output.
- `npm test` passes in full.

## Release Note

Fixed wrap-up counting open items from other runs' ledger files as if they belonged to the current run.

## Technical Approach

The probe already runs where a base ref is available: wrap-up's pack has the run's integration branch and merge base for its other probes. Derive owned files with `git diff --name-only {merge-base}...HEAD -- docs/plans/` through the probe's injectable `deps` seam, so the tests stay hermetic. Keep the existing #2563 rationale in mind. The over-count fallback existed because the only alternative was silently hiding the run's own items, and ownership-by-diff removes that dilemma. Update the comment block at `:380-396` to match.

### Key Files

- `plugin/bin/lib/wrap-up/pack.js` — `ledgerProbe` (366-418): ownership-based attribution plus an unattributed field
- `tests/bin-lib/wrap-up/pack.test.js` — inherited/owned ledger cases
- `plugin/skills/_shared/ledger-format.md` — read-only check: its Location section's "one ledger per pipeline run" wording should still hold after the change

## Gotchas

- A run whose ledger was created and committed earlier on the same branch still counts as owned, because the merge-base diff includes it. A ledger that only exists uncommitted in the worktree also needs handling. Include untracked or modified files from `git status --porcelain -- docs/plans/` along with the diff.
- Any consumer that reads `pack.ledger.files` (wrap-up's resolve gate, the Review Console) must not start treating the new unattributed field as blocking. Grep for `ledger.files` and `pack.ledger` consumers before changing the shape.
- The accumulation of finished runs' ledgers on `main` is itself a separate cleanup question. It is out of scope here, and the probe must be correct regardless.
