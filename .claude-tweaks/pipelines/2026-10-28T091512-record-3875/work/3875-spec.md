# 3875: Let E1 allow a multi-run reconciliation's conflict-resolution commit without closing sibling runs

Surface: infra

Origin: reflect hindsight from #3809
**Related:** #3973, #3736, #3744, #3822, #3876, #3900, #3915, #3974, #3975, #3978, #3979, #3983, #3989

## Current State

`plugin/skills/flow/worktree-merge.md` step 5's **Resolve now** bullet (line 127) carries a multi-run chase. A conflict resolution during a multi-run `local-merge` reconciliation ends in a `git commit`, and E1 (`runInner`'s tail loop in `plugin/bin/lib/hooks/pre-tool-use.js`) checks every commit against `ctx.runDir`, the newest non-terminal run in the project regardless of owner (`docs/hooks.md`'s "Two resolutions, not one"). The main checkout (or, under `worktree-always`, the scratch worktree the resolution runs in) is not any run's assigned worktree, so E1 denies unless the caller's ownership classifies as `foreign`, and the reconciling session usually owns the sibling runs. The procedure therefore closes this branch's run, then each other reconciliation branch's run E1 names in turn, and re-protects each one when the resolution lands or is abandoned.

That bullet drew #3809's whole-branch review Important 1, part of fix round 1, and four `/review` findings (3c at `:126` reproduced, plus single-agent 3b `:126`, 3c `:139`, 3f `:138`). The prose is correct today but is the most fragile part of the procedure, and it exists only because E1 cannot tell that a commit is concluding a merge of a live run's branch. E1's own deny message already names that case as legitimate ("If this checkout is intentionally correct (e.g. finishing the branch), clear the assignment first").

## Deliverables

- [ ] Add a live-query exemption to E1, of the same shape as `isIntegrationBranchFastForwardPush` (#2542): a `commit` target is allowed when its checkout has a merge in progress (a `MERGE_HEAD` exists) **and** every commit `MERGE_HEAD` lists equals the current `HEAD` of a live run's worktree (`ctx.runState.worktree` or any entry in E1's existing `otherWorktrees` map). Log a new `wd-merge-finish` event (expected, actual, merged run dir) to `ctx.runDir` and allow.
- [ ] Every unprovable answer keeps today's E1 verdict (no exemption): no readable `MERGE_HEAD`, a `MERGE_HEAD` commit matching no live run's worktree `HEAD`, a run worktree whose `HEAD` cannot be read (removed worktree, git failure, timeout), or a target action other than `commit`
- [ ] Simplify `worktree-merge.md` step 5's Resolve-now bullet: drop the E1 chase (closing and re-protecting other reconciliation branches' runs) and keep the per-branch close-run ordering #3809 pinned (this branch's run closed first, re-protected after a step 4 failure)
- [ ] Document the exemption in `docs/hooks.md` beside E1's posture bullets

## Acceptance Criteria

- In `tests/hooks-pre-tool-use.test.js`, a `git commit` in a checkout whose `MERGE_HEAD` equals a live sibling run's worktree `HEAD` is allowed and logs `wd-merge-finish`, while `ctx.runDir` names a different (newer) run
- The same commit is still denied when `MERGE_HEAD` is absent, when it names a commit that is no live run's worktree `HEAD`, when one of several `MERGE_HEAD` lines matches no live run, and when the matching run's worktree `HEAD` cannot be read. Each is its own test case.
- A `git push` or non-commit action is unaffected by the exemption
- Each new allow test goes red when the exemption is reverted (`git checkout --` on `pre-tool-use.js` only)
- `worktree-merge.md`'s Resolve-now bullet no longer instructs closing or re-protecting other branches' runs, and the existing #3809 ordering pins still pass
- `npm test` passes

## Release Note

Resolving a merge conflict during a multi-run local-merge reconciliation no longer has to close other branches' runs first.

## Technical Approach

The decision between the three signals the original request listed:

- **A run-state marker set and cleared by the reconciliation** was rejected. It adds a lifecycle (set before the merge, cleared on land or abandon) that the chase itself shows is fragile, and a marker left behind by a crash is a standing allow for that run's commits in the wrong checkout.
- **Narrowing E1's owner-unfiltered newest-run resolution in the main checkout** was rejected. The reconciling session usually owns the runs it merges, so their ownership verdict is `'mine'` and E1 would still deny. Narrowing further would also loosen E1 for the wrong-checkout commit it exists to catch.
- **A `MERGE_HEAD`-keyed live query** was chosen. Git already records the fact E1 lacks: a merge commit in progress whose parent-to-be is a live run's branch tip is that branch being integrated, not that run's work landing in the wrong checkout. It needs no new state, cannot go stale (git removes `MERGE_HEAD` when the merge concludes or aborts), and covers the `worktree-always` path too, where the resolution commits inside a scratch worktree that no run is assigned to.

Implementation follows `.claude/skills/pre-tool-use-gate-exemptions`: read `MERGE_HEAD` via `git rev-parse --git-path MERGE_HEAD` in the target's toplevel (a linked worktree's git dir differs from the main checkout's), compare commit ids exactly, read each candidate worktree's `HEAD` with `git -C {worktree} rev-parse HEAD`, resolve paths through `canonicalRealpath`, and fail closed on every inconclusive read.

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — E1 tail loop in `runInner`: the `MERGE_HEAD` live-query exemption and `wd-merge-finish` event
- `plugin/skills/flow/worktree-merge.md` — step 5 Resolve-now bullet: drop the E1 chase
- `docs/hooks.md` — E1 posture bullets
- `tests/hooks-pre-tool-use.test.js` — allow and fail-closed cases
- `plugin/bin/lib/hooks/context.js` — `appendEvent` (no change expected)

## Gotchas

- The exemption must sit after the `otherWorktrees` check and before the `foreign`-ownership branch. That way it never reclassifies a commit already allowed as `wd-ambiguous`, and a `foreign` caller keeps its existing allow + `systemMessage`.
- Under `worktree-always`, the fast-forward of the main checkout is `git merge --ff-only`, which is not a `commit` target, so only the scratch-worktree commit needs the exemption. Confirm with `gitTargetsFrom` before assuming otherwise.
- An octopus merge lists several commits in `MERGE_HEAD`; require every line to match, so a merge that also pulls in an unrelated branch keeps today's deny.
- The `worktree-merge.md` bullet is pinned by #3809's conformance tests; keep "this branch's run is closed first" and the step 4 re-protection wording intact.
