# 3014: flow-preflight's pr probe omits mergeable state, so a two-call dispatch resume misses a PR that turned CONFLICTING between calls

Surface: infra

**Related:** #2775, #2783, #2868, #2912, #2914, #2994, #3003, #3012, #3132

## Current State

When `/claude-tweaks:flow` adopts an inherited run directory, as `/claude-tweaks:dispatch`'s second call (`review,polish,wrap-up`) does, it gathers facts once via `bin/flow-preflight.js` (`plugin/skills/flow/steps-and-gates.md:56-60`). The pack's `pr` probe (`plugin/bin/lib/flow/preflight.js:263-268`) runs `gh pr view {n} --json state,isDraft,body` and returns `{number, url, branch, state, isDraft, checklist}`. It never reads `mergeable` or `mergeStateStatus`.

In the reported run (plugin 6.136.0), the integration branch moved between the two dispatch calls. A sibling PR edited the same two lines of two skill docs, so the run's PR became `CONFLICTING`. GitHub runs no `pull_request` CI on a conflicting PR, so the checks list held only the label workflow. The second call's verification stamp and the first call's decisions log both read green. The conflict surfaced only because the reviewer ran an ad-hoc `gh pr view --json mergeable`. Nothing in the pack, the adoption path, or `/review` Step 1.5 (`plugin/skills/review/code-mode-steps.md:57`) looks at mergeability.

## Deliverables

1. Extend the pack's `pr` probe to request `mergeable,mergeStateStatus` alongside `state,isDraft,body`, and return both fields. A forge or `gh` that omits them yields `null` for that field, never an error that fails the whole `pr` probe.
2. On the adopted-run path (`steps-and-gates.md`'s "Adopting an inherited run directory"), when the pack's `pr.mergeable` is `CONFLICTING`, print one visible line before any later phase runs: `Run PR #{n} is CONFLICTING with {integration branch} — CI will not run on it until the conflict is resolved.` Log it as an `AUTO` decision. Then reconcile per the existing catch-up procedure: merge the integration branch into the run branch, then re-verify. This is the same remedy `_shared/worktree-catchup-no-run-dir.md` and the phase-exit pushes already use. Cite the existing procedure; do not restate it.
3. When the merge in deliverable 2 itself conflicts, stop as a HARD-GATE failure with the conflicting paths named, rather than continuing to review on a stamp that no longer describes a mergeable tree.

## Acceptance Criteria

- A unit test feeds the `pr` probe a `gh` stub returning `mergeable: CONFLICTING` and asserts the pack's `pr` carries `mergeable` and `mergeStateStatus`. A stub omitting both asserts `null` values and `ok: true`.
- A test or conformance assertion pins the adopted-run path's `CONFLICTING` line and its routing to the catch-up procedure. It goes red against the current `steps-and-gates.md`.
- A `MERGEABLE` or `UNKNOWN` PR produces no new line, no new decision entry, and no behavior change. A test asserts this.
- Existing `tests/bin-lib/flow/preflight.test.js`, `tests/bin-lib/flow/preflight-cli.test.js`, and `tests/flow-preflight-conformance.test.js` pass, updated only where they pin the `pr` field's exact key set.
- `npm test` passes in full.

## Release Note

A resumed pipeline run now notices when its pull request has picked up a merge conflict since the last call, and catches up before reviewing.

## Technical Approach

Keep the change inside the probe that already reads the PR. One more pair of JSON fields on the same `gh pr view` call adds no new network round-trip. The adoption-path handling is prose in `steps-and-gates.md`, keyed off the pack field, so the decision stays mechanical and is never re-derived by hand. `UNKNOWN` is GitHub's transient value while it computes mergeability, so it must stay a no-op, as the original request asks. The merge gate re-reads mergeability at merge time anyway.

### Key Files

- `plugin/bin/lib/flow/preflight.js` — `pr` probe (`:263-268`) requests and returns `mergeable`/`mergeStateStatus`
- `plugin/skills/flow/steps-and-gates.md` — "Adopting an inherited run directory" (`:56`) surfaces a `CONFLICTING` PR and routes to catch-up
- `tests/bin-lib/flow/preflight.test.js` — `pr` probe field assertions
- `tests/flow-preflight-conformance.test.js` — adoption-path prose pin

## Gotchas

- The pack field set may be pinned by conformance tests and consumed by other readers of `preflight.json`. Add fields; never rename or drop `state`/`isDraft`/`checklist`.
- `mergeable` is computed lazily by GitHub. A first read right after a push often returns `UNKNOWN`. Do not poll in the probe, because the pack has a probe timeout (`PROBE_TIMEOUT_MS`, `preflight.js:284`).
- #3013 (ready) adds a PR-check read to `/test` and `/review` Step 1.5. A conflicting PR has no CI, so an empty check rollup there would read as pending. These two records cover different signals. Keep the `CONFLICTING` handling on the adoption path, as this record specifies, and do not fold it into #3013's check read.

## Build alignment notes

Deviations from the spec text found at `/claude-tweaks:build` Common Step 4.5, all classified Beneficial (kept as built):

- The pack's `pr` value also carries `conflictNote` — the exported `PR_CONFLICT_NOTE` literal filled in — so the adoption-path prose prints a code-owned string verbatim (the `ADOPTION_NOTES` pattern) instead of composing the line by hand.
- `conflictNote` is set only for an `OPEN` PR reading `CONFLICTING`, matching `bin/pr-merge-state.js`'s exclusion of closed/merged PRs; a closed PR's stale mergeability is no signal for the run.
- The new adopted-run stop is registered in `_shared/auto-mode-contract.md`'s HARD-GATE / BLOCKED / STOP row, as every mid-flow `auto` stop must be; the abort path logs its own `AUTO` entry and names the resume form.

## Original request

flow-preflight's pr probe omits mergeable state, so a two-call dispatch resume misses a PR that turned CONFLICTING between calls

**Kind:** Gap

**Affected component:** bin/flow-preflight.js (pr probe), skills/flow/steps-and-gates.md (Adopting an inherited run directory)

## Current State

On a `/claude-tweaks:dispatch` two-call handoff (`build,test`, then `review,polish,wrap-up` against the same `PIPELINE_RUN_DIR`), the second call's `flow-preflight.js` pack reports `pr: {number, url, branch, state, isDraft, checklist}`. It does not report `mergeable`. In one run the integration branch moved between the two calls. A sibling PR edited the same two lines of two skill docs, so the run's PR was `CONFLICTING`. The forge then ran no `pull_request` CI on it (GitHub skips CI on conflicting PRs). The second call's verification stamp and the first call's decisions log both read green. The conflict surfaced only because the reviewer ran an ad-hoc `gh pr view --json mergeable` and found just the label workflow in the checks list. Nothing in the pack or in review Step 1.5/2 checks it.

## Deliverables

- Add `mergeable` (and `mergeStateStatus` where the forge supports it) to the pack's `pr` probe.
- When it reads `CONFLICTING`, surface it on the adopted-run path, before review's test gate trusts a stamp. Either say how to reconcile (merge the integration branch in, then re-verify) or make it an explicit gate.

## Acceptance Criteria

- A resumed run whose PR is `CONFLICTING` prints a visible line naming the conflict before review starts.
- A `MERGEABLE` or `UNKNOWN` PR changes nothing.
