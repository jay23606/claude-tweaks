# 2912: Two-call /flow dispatch (build,test then review,polish,wrap-up) can leave the run with no materialize commit and no draft PR on the shared branch

Surface: infra

**Related:** #2914

## Current State

`/claude-tweaks:dispatch` Step 5 splits one record's pipeline into two `/flow` calls that share one run directory via `PIPELINE_RUN_DIR`: `/flow #N build,test`, then `/flow #N review,polish,wrap-up` (the "Intentional two-call consumer" contract, `plugin/skills/flow/steps-and-gates.md:54`). The second call is supposed to adopt a fully set-up run (adoption case 1 in `plugin/bin/lib/flow/preflight.js`).

In run `2026-10-02T182455-record-2765` (record #2765), call 2's adoption probe reported case 3 instead — "Recovering inherited run directory ... missing config.yml; backfilled worktree registration, PR-early lifecycle, materialize commit before proceeding" (`preflight.js:48`). Call 1 had committed and pushed its build fix (`99fa1f73b`, branch `worktree-flow-spec-2765` on origin), but:

- never committed `work/2765-spec.md` (the `materialize.md` Resolution + Materialization step),
- never ran `_shared/pr-early-run-lifecycle.md`'s push-and-open-draft-PR step (`run-state.json` had no `pr`),
- logged its Step 2.8 claim as "Step 2.8: claimed issue #2765" instead of the canonical "Step 2.8: claimed #2765" that the `pre-tool-use.js` stamps gate matches, which later denied call 2's first push.

Call 2 backfilled all three by hand. The root cause is not confirmed. Candidates:

1. `/claude-tweaks:dispatch` Step 4's materialize-before-claim minting substituting for `/flow`'s own Step 1 materialize on the two-call path and skipping the commit/push/PR sequence.
2. A build invoked directly by dispatch, bypassing `/flow` Step 4's materialize-commit.
3. A stale reclaimed tombstone from the earlier run `2026-10-02T122146-record-2765` (its PR #2881 closed unmerged) confusing the bookkeeping for the fresh run that reused the record.

## Deliverables

1. Trace call 1's actual path for a record that previously held a reclaimed tombstone claim and identify which step skipped the materialize commit and the draft-PR open. Record the finding in the PR description, naming which of the three candidates (or another cause) it was.
2. Fix that path so call 1 alone always leaves: a committed `work/{n}-spec.md` on the run's branch, `run-state.json.worktree`, and (under `integration-model: pr-first`) `run-state.json.pr` with a live draft PR.
3. Make the Step 2.8 claim line on this path come from the canonical writer (`plugin/bin/claim-targets.js` or the documented `log-decision.js` text) so it always matches the stamps gate's regex; no free-hand claim-line phrasing.
4. A regression test at the level the root cause lives (preflight adoption fixture, dispatch/flow CLI, or claim-line writer) that fails on the pre-fix behavior.

## Acceptance Criteria

1. A fresh two-call dispatch (`/flow #N build,test`, then `/flow #N review,polish,wrap-up`) against a record that previously held a stale, reclaimed tombstone claim produces, after call 1 alone: a committed `work/{n}-spec.md`, a recorded `run-state.json.worktree`, and under `pr-first` a recorded `run-state.json.pr` with a live draft PR.
2. Call 2's adoption probe reports case 1, not case 3, in that scenario.
3. The claim line written on this path matches `Step 2\.8: claimed #{n}\b`.
4. The new regression test fails before the fix and passes after it; the affected suites pass.

- logged its Step 2.8 claim line with non-canonical phrasing ("Step 2.8: claimed issue #2765" instead of the `pre-tool-use.js` gate's exact-match regex `Step 2\.8: claimed #{n}\b` — i.e. "claimed #2765"), which later denied call 2's first push attempt.

Root cause is **not confirmed** — candidates include: `/claude-tweaks:dispatch`'s own materialize-before-claim minting (`dispatch/SKILL.md` Step 4) racing or substituting for flow's own Step 1 materialize in a way that skips the commit/push/PR-open sequence on the two-call path specifically; a build invoked directly by dispatch bypassing `/flow`'s Step 4.2 materialize-commit step entirely; or an earlier partial run (`decisions.md`'s line 1 mentions "reclaimed stale tombstone from run `2026-10-02T122146-record-2765`, reason already-shipped") whose own PR (`#2881`, closed unmerged) confused the bookkeeping for the fresh run that reused the issue.
