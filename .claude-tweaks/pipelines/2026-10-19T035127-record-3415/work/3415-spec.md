# 3415: One reader for installed_plugins.json — Impeccable's resolver ignores CLAUDE_CONFIG_DIR and compares case-echoed paths

Surface: infra

**Related:** #3414

## Current State

Two modules build the path to Claude Code's `installed_plugins.json` and read it themselves, and they disagree in three ways (verified against origin/main at 7852fd8bf):

- **Config dir.** `plugin/bin/lib/impeccable-engine/index.js`'s `readInstalledPlugins` (line 108) builds `path.join(deps.homedir(), '.claude', 'plugins', 'installed_plugins.json')` and ignores `CLAUDE_CONFIG_DIR`. `plugin/bin/lib/superpowers-version.js`'s `effectiveSuperpowersVersion` (line 79) resolves `deps.env.CLAUDE_CONFIG_DIR || path.join(deps.homedir(), '.claude')`, the same rule `plugin/bin/dream-scan.js` uses (line 66). A user who sets `CLAUDE_CONFIG_DIR` (the maintainer's own machine does) therefore gets Impeccable `not-installed` from `node plugin/bin/impeccable-engine.js resolve` while the SessionStart superpowers notice still finds its install.
- **Realpath.** Impeccable's `defaultDeps()` (line 61) injects `realpath: (p) => fs.realpathSync(p)`. The JS form echoes the input's casing on a case-insensitive volume, so a mis-cased cwd or `projectPath` fails `selectEntry`'s ancestor match. `superpowers-version.js`'s `defaultDeps()` (line 69) injects `fs.realpathSync.native`, which canonicalizes case; its comment records why.
- **Home-directory entries.** The #3380 probe found that Claude Code never applies a project-scope entry whose `projectPath` is the home directory. `selectEntry` in `plugin/bin/lib/installed-plugins.js` exposes this as `opts.excludeHome`; `superpowers-version.js` passes it (line 101), Impeccable's `resolve()` (line 178) does not. The shared module's header comment says Impeccable "keeps today's rule … changing it there is a separate decision" — this record is that decision.

`selectEntry` and `safeRealpath` already live in the shared `plugin/bin/lib/installed-plugins.js`; the file read and its config-dir resolution did not move with them. The two failure shapes differ by design: Impeccable's `resolve()` returns `{ok:false, reason:'not-installed', fix, detail}`, where `detail` today is `not found: {file}`, `malformed JSON (…)`, or the read error's message; `effectiveSuperpowersVersion` returns null on any failure.

Three docs restate the home-only path: `docs/plugin-structure.md` line 65 (`~/.claude/plugins/installed_plugins.json` for impeccable-engine), line 66 (installed-plugins.js's entry), and `plugin/skills/design-wrapper/modes/explore.md` line 38.

## Deliverables

It resolves the file as `path.join(env.CLAUDE_CONFIG_DIR || path.join(homedir(), '.claude'), 'plugins', 'installed_plugins.json')`. A missing `deps.env` means no override; the helper never reaches for `process.env` itself, so the env comes only from each resolver's `defaultDeps()`.
2. Replace Impeccable's local `readInstalledPlugins` with the shared one. Map its failure to the existing `{ok:false, reason:'not-installed', fix: NOT_INSTALLED_FIX, detail}` and keep the three `detail` forms (`not found: {file}`, `malformed JSON (…)`, the read error's message). `FAILURE_REASONS` stays unchanged. Impeccable's `defaultDeps()` gains `env: process.env`.
3. Replace `superpowers-version.js`'s inline path build and read with the shared reader, keeping its `null`-on-any-failure contract.
4. Default Impeccable's `realpath` to `fs.realpathSync.native`, matching `superpowers-version.js`.
5. Decide `excludeHome` for Impeccable with the same kind of headless probe #3380 used: does a project-scope `impeccable@impeccable` entry whose `projectPath` is the home directory ever load in a session under it? Either way, record the probe result and the decision in `installed-plugins.js`'s header comment, replacing the "separate decision" sentence.
6. Update the three doc lines named in Current State to state the `$CLAUDE_CONFIG_DIR` (default `~/.claude`) location, and the Impeccable `excludeHome` outcome in `docs/plugin-structure.md`'s installed-plugins entry.

## Technical Approach

Move the reader into the module that already owns entry selection, so both resolvers share one path rule and one parse. Each resolver keeps its own error shape by mapping the shared `{ok:false, detail}` result: Impeccable wraps it as `not-installed`, and superpowers returns `null`. Keep Impeccable's `exists`-then-read behavior observable only through the `detail` strings. The shared reader can catch `ENOENT` from `readFile` and produce `not found: {file}`, so the existing `exists` dep stays only for the launcher check.

Do the realpath switch in `defaultDeps()` only; tests that inject their own `realpath` are unaffected. `safeRealpath` already passes the injected function through unchanged.

The `excludeHome` probe is the build's one empirical step. Run it the way #3380 did (headless `claude -p` init events from the home directory and from a directory under it, with a home-directory project-scope Impeccable entry present) and record the observed result before choosing.

## Gotchas

- `CLAUDE_CONFIG_DIR` is set on the maintainer's machine. If the shared reader fell back to `process.env` when `deps.env` is absent, the real-file tests in `resolve.test.js` (the #3040 hang test) and `run.test.js` (the timeout test), which build full deps objects without `env`, would read the real account config instead of their temp home and fail or pass for the wrong reason. Missing `deps.env` must mean no override.
- `FAILURE_REASONS` is a frozen contract that sibling consumers test against. The config-dir change must not add a reason; a missing file under the resolved config dir is still `not-installed`.
- On macOS `os.tmpdir()` sits under `/var`, a symlink to `/private/var`. Native realpath resolves it, so build test fixtures from realpathed temp dirs before comparing paths.
- Related open record #3414 (`selectEntry` and `..`-prefixed directory names) touches the same module. The `installed-plugins.js` comment cites #3417 for that fix, so check #3414's state before building, to avoid a conflicting edit.
