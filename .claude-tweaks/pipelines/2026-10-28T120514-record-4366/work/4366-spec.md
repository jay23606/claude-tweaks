# 4366: pr-checks.js cannot see a merge-conflicted PR: the review PR-check gate lets a DIRTY PR with no CI through

Surface: infra

**Related:** #4025, #4354, #4168, #2986, #3014, #3013, #3469, #4304, #4343, #4395, #3905, #4345

Origin: reflect full from #4025

Defer-reason: tangential

## Current State

During #4025's review, PR #4354 was `DIRTY`, conflicting with main after #4168 landed, and had run no CI beyond the label workflows. The reviewer found the conflict by reading the PR state by hand, about 3 hours after the build opened the PR.

`bin/pr-checks.js` is the one read `/claude-tweaks:test`'s pipeline gate and `/claude-tweaks:review` Step 1.5 both run (`_shared/pr-check-gate.md`). Probed at HEAD, its `gh pr view` asks only for `headRefOid,statusCheckRollup,baseRefName` (`pr-checks.js:187`), and its states are `red | inherited-red | pending | stale | green | no-ci | read-failed | no-pr | gh-absent`. A conflicted PR with no check runs therefore reads `no-ci`, a fail-open `SKIP` ("local verification only"), or `pending` when the repo has pull_request CI (`classify.js:77`). The review gate table (`review/code-mode-steps.md:108-109`) proceeds on anything but `red`.

Premise correction: the plugin already detects a conflicted PR, but only at phase exits. `bin/pr-merge-state.js` (#2986) runs after every phase-exit push through `phase-exit.js`, classifies with an exported `classifyMergeState` (`pr-merge-state.js:63-69`, exported at `:148`: `DIRTY` or `CONFLICTING` is conclusive, `UNKNOWN` is no signal), and is routed by `_shared/git-discipline.md`'s Post-push merge-state check. The gap is a base that moves after the last phase-exit push. The next gate reads checks only, and the `--pr` display readers (`_shared/github-pr-scan.md`, `wrap-up/pack.js`, `dispatch/settle-parked.md`) count such a PR as `no-ci`. `bin/lib/flow/preflight.js:294-310` holds a third, inline `CONFLICTING` check (#3014).

## Deliverables

1. Add a `conflicting` state to `pr-checks.js`. Request `mergeable,mergeStateStatus` in its existing `gh pr view` call and classify with `pr-merge-state.js`'s `classifyMergeState`, moved to a shared lib module both CLIs import, not copied. Carry `mergeStateStatus`, `mergeable` and `baseBranch` (the PR's `baseRefName`) in the envelope.
2. Precedence: `conflicting` replaces every check-derived state (`red`, `inherited-red`, `pending`, `green`, `no-ci`), because a conflicted PR gets no new `pull_request` runs, so its checks say nothing about HEAD. `stale` still wins, because a local HEAD ahead of the PR may already hold the catch-up. `no-pr`, `gh-absent` and a failed `gh pr view` stay as they are. `unknown` merge state changes nothing.
3. Route `conflicting` in `_shared/pr-check-gate.md` by citing `_shared/git-discipline.md`'s Post-push merge-state check routing rather than restating it. In `auto`/`confirm`, run its Catch-up, then re-run the gate once. In `interactive`/`hybrid`, stop at the gate and give the catch-up commands. The CLI's own `--run` decisions.md line for `conflicting` is one `AUTO` entry naming the PR and base.
4. Add the `conflicting` row to `review/code-mode-steps.md`'s Step 1.5 gate table, citing `pr-check-gate.md`, and map the state in every `pr-checks.js --pr` reader: `_shared/github-pr-scan.md`'s count (not a green or `no-ci` candidate), `wrap-up/pack.js` and `dispatch/settle-parked.md`.
5. Update `pr-checks.js`'s header comment, its USAGE state list, and `docs/plugin-structure.md`'s state list where they enumerate states.

## Acceptance Criteria

- A fixture PR view with `mergeStateStatus: DIRTY` and no check runs classifies `conflicting`, not `no-ci`, `pending` or `green`. So does `mergeable: CONFLICTING` with `mergeStateStatus: BLOCKED`.
- `mergeStateStatus: UNKNOWN` with `mergeable: UNKNOWN` leaves the check-derived state unchanged.
- A `DIRTY` view whose `headRefOid` differs from local HEAD reads `stale`, not `conflicting`.
- `pr-merge-state.js`'s outputs are byte-identical on its existing tests after `classifyMergeState` moves, and both CLIs import the one function.
- Under `--run`, a `conflicting` read writes one `AUTO` `PR-check gate` entry. `--pr` writes nothing.
- `review/code-mode-steps.md`'s gate table and `pr-check-gate.md`'s routing name `conflicting`. Every `pr-checks.js --pr` reader maps it, so none treats it as green or `no-ci`.
- `npm test` passes.

## Release Note

The test and review gates now notice when a pull request has fallen into a merge conflict, so the run catches up instead of reviewing a branch that will never get CI.

## Technical Approach

Move `classifyMergeState` into `plugin/bin/lib/pr-checks/classify.js`, the classification lib `pr-checks.js` already imports, or into a small sibling module, and have `pr-merge-state.js` import it from there. Apply it in `classifyPr` after the rollup verdict, so the precedence rule in Deliverable 2 lives in one place. Routing stays in prose by citation: `pr-check-gate.md` points at `git-discipline.md`'s Post-push merge-state check and Catch-up for the action, so the two conflict routes cannot drift.

## Gotchas

- Auto-mode contract: a new mid-flow stop in `auto` is forbidden unless it is a HARD-GATE (`_shared/auto-mode-contract.md`). A merge conflict is not a test failure, so `auto` runs the catch-up instead of stopping. Only `interactive`/`hybrid` stop.
- GitHub computes mergeability asynchronously, so `UNKNOWN` is common right after a push. Never read it as a conflict and never re-read inside this CLI, the same rule `pr-merge-state.js` follows.
- Expand-contract: an installed build's prose may read an older `pr-checks.js`, and a newer CLI's `conflicting` may reach older prose that lacks the row. Older routing falls to its own default, which must not read it as green. Check each consumer's unknown-state fallback, and land the prose rows in the same release as the CLI state.
- `pr-checks.js`'s state list is enumerated in its header comment, its USAGE and `docs/plugin-structure.md`, and `pr-merge-state.js`'s `STATES` is pinned to prose by `tests/git-discipline-merge-state-conformance.test.js`. Find every enumeration with `git grep -n "no-ci | read-failed"` and update them together.
- `preflight.js`'s inline `CONFLICTING` check (#3014) is a third copy. Importing the shared classifier there is in scope only if it is a one-line swap with unchanged output, otherwise leave it.
- #4304 (catch-up before the whole-branch review) and #4343 (catch-up before build's final verification) add proactive catch-ups at other points. They narrow the window but do not remove it, because the base can still move after them, so this gate-time detection stays needed. #4395 edits the same Step 1.5 gate table (its `verifiedHead: false` row). Rebase onto whichever lands first.

## Current State

During #4025's review, PR #4354 was `DIRTY` (a merge conflict with main after #4168 landed) and had run no CI beyond the label workflows. `bin/pr-checks.js` and `bin/lib/pr-checks/classify.js` classify only check runs (`red|pending|stale|green|no-ci|...`); nothing in them reads `mergeStateStatus`, so the review Step 1.5 PR-check gate cannot tell a clean PR from one that is conflicted and therefore never gets CI. The conflict was found only because the reviewer read the PR state by hand, ~3 hours after the build opened it.

## Deliverables

Make `pr-checks.js` report a conflicted PR (`mergeStateStatus` `DIRTY`, or `mergeable` `CONFLICTING`) as its own state, distinct from `no-ci`, with the conflicting base named.

Have review Step 1.5 (`review/code-mode-steps.md`) stop on that state with the catch-up instruction (`_shared/git-discipline.md`, Catching a branch up with main) instead of proceeding to the lenses.

## Acceptance Criteria

A fixture PR with `mergeStateStatus: DIRTY` and no check runs classifies as the new conflicted state, not `no-ci` or `green`.

The review gate table maps the conflicted state to a stop with the catch-up command.

A review now stops at once when its pull request has a merge conflict, instead of reviewing a branch that can never get CI.
