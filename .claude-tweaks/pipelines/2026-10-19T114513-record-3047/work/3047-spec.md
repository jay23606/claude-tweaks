# 3047: review Step 6.7: an auto-applied fix wave changes the UI after /test's QA stories ran, and nothing marks that evidence stale

Surface: infra

**Related:** #3048

## Current State

`/claude-tweaks:review`'s Step 6.7 (Late Findings Routing, `plugin/skills/review/code-mode-steps.md:327`) consolidates the actionable findings from Steps 6, 6.5, 6.6, 6.65 and 6.66 into one table. Under a pipeline run it routes each finding by the resolved `review-auto-apply-ceiling` (`code-mode-steps.md:340`, `step3-routing.md`'s ceiling-keyed table). At `medium`, Low and Medium findings auto-apply as fix commits (`_shared/policy-schema.md:192`). Step 6.7 then folds each finding into its Step 7 summary section (`code-mode-steps.md:343`). It runs no QA story re-run, and nothing records that QA ran before those fixes.

`/claude-tweaks:test` ran the record's QA stories earlier in the pipeline. The QA line in `review-summary-template.md:53-61` (`### QA Validation (from /test)`, statuses ALL PASSED / PASSED WITH OBSERVATIONS / …) reports that earlier result with no freshness qualifier. The infrastructure to re-run only affected stories already exists. `/claude-tweaks:test qa affected` (`plugin/skills/test/SKILL.md:44`) selects stories whose `source_files` intersect `verify.js --changed-files`, and stories carry a mandatory `source_files` array (`plugin/skills/stories/source-aware-design.md:66`).

Observed (reporter, 6.136.0): a single-record `auto` `/flow` run on a web UI record with `review-auto-apply-ceiling: medium`. Step 6.5 returned nine low/medium design findings, and Step 6.7 auto-applied them as nine commits that changed behaviour the passing stories describe (tooltip placement, focus/scroll after paging, a new pending state). One story's `verify` text was edited by the wave. Types/lint/tests/e2e were re-verified, but the QA stories were not re-run. The summary still read "QA: all passed" for a UI ten commits old, and the controller re-ran the stories by hand.

## Deliverables

1. In `code-mode-steps.md` Step 6.7, after the resolved fixes are applied: when any applied fix touched a file listed in a QA story's `source_files`, re-run those stories via `/claude-tweaks:test qa affected` (scoped to the fix wave's changed files), and fold the result into the Step 7 QA line.
2. In `review-summary-template.md`'s QA Validation section, add a freshness qualifier for the case where QA was not re-run after an applied fix wave touching story `source_files` (for example when no dev server or browser is available): `{status} — ran before the review's fix wave ({N} commits since); stories touching changed files: {ids}`.
3. Apply the same rule to fixes applied interactively through Step 6.7's batch table ("Fix now"), not only auto-applied ones.

## Acceptance Criteria

- `code-mode-steps.md` Step 6.7 names the post-wave re-run of affected QA stories via `/claude-tweaks:test qa affected`, gated on an applied fix touching any story's `source_files`.
- When no applied fix touches any story's `source_files`, Step 6.7 runs no QA re-run (no added cost for non-UI waves).
- `review-summary-template.md` documents the stale-QA qualifier and when it renders (applied wave touched story `source_files` and the re-run did not happen).
- The verdict comment's QA reporting reads the same qualified status (no separate wording).
- `code-mode-steps.md` stays under the per-file byte ceiling (`CEILING_BYTES`, `plugin/bin/lib/skill-audit/context-cost.js:31`), and `npm test` passes.

## Release Note

Re-run affected QA stories after review auto-applies UI fixes, so the review summary never reports QA results for a UI that has since changed.

## Technical Approach

Prefer re-running over annotating. `test qa affected` already does the story selection, so the re-run reuses an existing mode instead of adding a new staleness mechanism. The qualifier only covers the case where a re-run cannot happen. The changed-file set for the wave is the files the Step 6.7 fix commits touched. Pass it the way `test/SKILL.md`'s `affected` mode documents (`verify.js --changed-files`), so stories untouched by the wave are not re-run.

### Key Files

- `plugin/skills/review/code-mode-steps.md` — Step 6.7 post-wave affected-story re-run
- `plugin/skills/review/review-summary-template.md` — stale-QA qualifier on the QA Validation line

## Gotchas

- `code-mode-steps.md` is 41465 B against a 46080 B ceiling. Keep the Step 6.7 addition short, or cite a sub-file, as `focus-criterion-passes.md` already does for Steps 6.6-6.66.
- Out of scope: the reporter's related idea of running `design-wrapper review` before `/test`'s QA on web-surface records. That is a pipeline step-order change with its own cost tradeoff. File it separately if wanted.
- Step 3 Routing's own fix-now path (`code-mode-steps.md:258`) runs before Steps 4-7 and can also touch UI. This record is scoped to Step 6.7's late wave, the observed case.
- In a headless run with no dev server, the re-run self-skips. The qualifier must then render rather than silently reporting the pre-wave status.

## Original request

review Step 6.7: an auto-applied fix wave changes the UI after /test's QA stories ran, and nothing marks that evidence stale

**Summary:** `/review` Step 6.7 can auto-apply a fix wave that changes rendered UI after `/test`'s QA stories ran, and nothing re-runs those stories or marks the QA result as older than the wave.

**Kind:** Gap

**Affected component:** `/claude-tweaks:review` (code-mode Step 6.7, late findings routing) and the `/claude-tweaks:flow` step order

**Use case:**
A single-record `/flow` run in `auto` mode on a web UI record, `review-auto-apply-ceiling: medium`.

`/test` ran the record's QA stories (all passed). `/review` Step 6.5 (the design critique and audit) then returned nine low and medium findings. Under the ceiling, Step 6.7 auto-applied all of them as a fix wave of nine commits. Those commits changed rendered behaviour the stories describe: where two tooltips open, where focus and scroll land after paging, a new pending state on a control. One story's `verify` text had to be edited by the wave to stay true.

After the wave the pipeline re-verifies types, lint, tests and e2e (scoped per `test/verification.md`), but QA stories are not re-run, and nothing in the review summary, the verdict comment or the pipeline summary says the QA result predates the wave. "QA: all passed" then describes a UI ten commits old. In the observed run the controller noticed and re-ran the affected stories by hand.

Either of these would close it:

1. When Step 6.7 auto-applies a finding that touches a file listed in any story's `source_files`, mark those stories stale and re-run them after the wave, with the same tiering `/test` uses.
2. Have the review summary's QA line say so: "ran before the review's fix wave (N commits since); stories touching changed files: ...".

Related observation: the design pass is the last source of findings in `/review`, so on a UI record its fixes land after the most expensive verification (in the observed run a full verification had to be repeated). An option to run `design-wrapper review` before `/test`'s QA on records with a web surface would put those findings in front of QA instead of behind it.

Cost in the observed run: one extra full verification and a manual QA re-run.
