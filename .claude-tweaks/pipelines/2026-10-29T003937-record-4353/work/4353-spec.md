# 4353: Worktree Bash guard again refuses spec-status --status complete (regression of #1651, 6.153.0)

Surface: infra

**Related:** #1651, #3340, #4028, #347, #4283, #3822, #4217, #4345, #3978, #4125

Origin: upstream feedback from an unattended multi-spec `/flow` run's consolidated Review Console (#347)

## Current State

In a worktree-isolated session, `node <plugin>/bin/hooks.js spec-status --run <parent> --spec <n> --status complete --phase wrap-up` is refused with "runs a string through complete, which can't be verified to stay inside the worktree". It is refused alone and as the second command after `;`. The workaround the reporter used was a `node -e` call that builds the word from parts.

Premise correction: this is not a regression of a #1651 fix. The refusal comes from the Claude Code harness's worktree-isolation guard, not from this plugin. #1651 could not change the guard, so it documented the shape and its workaround instead. `plugin/skills/_shared/scratch-worktree.md` §7 lists "Literal token `complete` as an argument" as `refused`, last verified 2026-10-20 (#3340), with the composed-word `node -e` workaround. The documented completion call has used that composed form since #1651 (`plugin/skills/flow/multispec-progress-banner.md:22-26`, commit 11e73372b). `multispec-review-console.md`'s re-entry step 4 names no `spec-status` call. So the documented command works, and the run's refusal came from typing the plain form the docs warn against.

The real cost is that the only safe spelling of the most frequent multi-spec transition is a fragile one-liner. It holds a `${CLAUDE_PLUGIN_ROOT}` splice inside `node -e` text and a hand-built argv, so an agent reaching for the plain command walks into the refusal first.

`hooks.js` reads flag values only in the spaced form. `flagVal` (`plugin/bin/hooks.js:216-219`) is `args.indexOf(name)` plus the next token, and `resolveRunArg` uses `args.indexOf('--run')` (`:405`). `firstUnknownFlag` (`:201`) treats any `--*` token not in `KNOWN_FLAGS` as unknown, so `--status=complete` is refused as an unknown flag today. The repo's own model of the guard says a shell word that only contains `complete` passes, and only a whole word `complete` is refused (`tools/guard-refusals/shapes.js:185-189`, the `complete-token` detector at `:387`). That predicts `--status=complete`, one shell word, passes the guard.

## Release Note

Multi-spec `/flow` runs in a worktree can mark a spec finished with a plain `spec-status --status=complete` command instead of a composed `node -e` workaround.

## Technical Approach

Parse `--name=value` once, in a small helper used by `flagVal`, `firstUnknownFlag` and `resolveRunArg`: split on the first `=` when the name part is a declared value flag. Keep `VALUE_FLAGS` as the single list of flags that take a value. A parse-on-every-call shim in `runSpecStatus` alone would leave the other verbs inconsistent, so it is the wrong place.

### Key Files

- `plugin/bin/hooks.js` — `flagVal`, `firstUnknownFlag`, `resolveRunArg`, `VALUE_FLAGS`
- `plugin/skills/flow/multispec-progress-banner.md` — the completion call

- `tests/hooks-help-guard.test.js` — unknown-flag guard with the `=` form

## Original request

Worktree Bash guard again refuses spec-status --status complete (regression of #1651, 6.153.0)

Regression of #1651 on plugin 6.153.0.

In a worktree-isolated session, the Bash guard refuses the documented multi-spec completion call:

```
node <plugin>/bin/hooks.js spec-status --run <parent-run-dir> --spec 812 --status complete --phase wrap-up
```

The refusal message is "this command runs a string through complete, which can't be verified to stay inside the worktree". The guard reads the argument value `complete` as the bash builtin `complete`. The same refusal appears when the call is the second command after `;`, and when it is the only command in the Bash call. `--status=complete` is not accepted by `spec-status`'s parser, so the spelled-out form is the only documented one (`flow/multispec-progress-banner.md`, `flow/multispec-review-console.md` re-entry step 4).

**Impact:** an in-worktree multi-spec `/flow` run cannot mark a spec finished through the documented command, which leaves the manifest stale and blocks the consolidated pass's eligibility check.

**Workaround used:** `node -e "require('child_process').execFileSync(process.execPath,[hooks,'spec-status',...,'--status','comp'+'lete',...])"`.

**Expected:** the guard treats `complete` as an argument when it is not in command position (the #1651 fix), or `spec-status` also accepts `--status=complete`.
